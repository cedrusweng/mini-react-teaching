Fiber 结构与使用方法

基于 src/reconciler/ReactFiber.js，说明每个字段的职责、Fiber 树的连接方式，以及协调器如何创建和复用 Fiber。

源码位置：src/reconciler/ReactFiber.js配套：ReactFiberWorkLoop / BeginWork / CommitWork

1. Fiber 是什么

Fiber 是协调器的最小工作单元，也是一个普通的 JS 对象。它把「组件 / DOM 节点」描述成可中断、可复用的链表节点：

  • Element → Fiber → DOM：createElement 产出不可变描述，Fiber 持有运行期状态、宿主实例和副作用。
  • 一个 Fiber 对应一次渲染中的某个节点；函数组件 Fiber 没有自己的 DOM，靠 stateNode 为空来区分。
  • 多个 Fiber 通过 child / sibling / return 连成树，遍历时本质是一条可逐节点推进的链表。
  • 每次更新会构建一棵 workInProgress 树，与已提交的 current 树通过 alternate 互相指向，即「双缓冲」。
一句话记忆：tag/type/key 决定「它是谁」，child/sibling/return 决定「它在哪」，pendingProps/memoizedProps/memoizedState 决定「它的数据」；stateNode/alternate/effectTag 决定「怎么更新」。

3. Fiber 树的数据结构

Fiber 树并不是「父节点持有 children 数组」的普通树，而是由 Fiber 对象通过 child / sibling / return 三个指针连成的有序链表树。

三个核心指针

指针指向说明
child第一个子 Fiber一个父节点只保存「长子」，其余子节点不放在数组里。
sibling下一个兄弟 Fiber兄弟节点横向串联，最后一个兄弟的 sibling 为 null。
return父 Fiber是 Fiber 树上的父节点，不一定是最近的 DOM 父节点；函数组件会被跳过。

拓扑示例

HostRoot
  └─ child → div
               └─ child → h1 ──sibling──→ p
                            │              │
                          child          child
                            ↓              ↓
                          text1          text2

指针关系：
hostRoot.child = div;  div.return = hostRoot;
div.child = h1;        h1.return = div;
h1.sibling = p;        p.return = div;
h1.child = text1;      text1.return = h1;
p.child = text2;       text2.return = p;

根节点与 FiberRoot

Root 不是普通 Fiber，而是一个额外的 FiberRoot 对象，它与 HostRoot Fiber 互相引用：

export function createFiberRoot(containerInfo) {
  const root = { containerInfo, current: null, finishedWork: null };
  const hostRootFiber = createHostRootFiber();
  hostRootFiber.stateNode = root;   // Fiber → FiberRoot
  root.current = hostRootFiber;     // FiberRoot → 当前 Fiber 树
  return root;
}

这样任意子 Fiber 沿 return 一路向上都能找到 FiberRoot；Hooks 的 setState 正是通过这条链触发调度。

为什么用这种结构

  • 可中断遍历：工作循环只需一个 nextUnitOfWork 指针，沿 child / sibling / return 推进，不依赖递归调用栈。
  • 统一子节点处理：无论 JSX 里写几个孩子，Fiber 层统一看成「第一个 child + 一串 sibling」。
  • 便于复用：协调时逐项比较 oldFiber 与 element，同 type/key 就通过 alternate 复用节点。
  • 提交顺序清晰：删除用 deletions 列表，插入/更新按 child → sibling 深度优先执行。
遍历口诀：beginWork 后若有 child 就向下；没有则 completeWork，有 sibling 转兄弟，否则沿 return 上升，直到回到根且无兄弟。

    5. 双缓存（Double Buffering）机制原理

    双缓存的核心是：内存中同时保留两棵 Fiber 树。一棵是已经提交、与屏幕 DOM 对应的 current 树；另一棵是在后台构建的 workInProgress（WIP）树。render 阶段只在 WIP 上工作，不碰真实 DOM；直到 commit 阶段才一次性把变更落地，并切换 root.current。

    ① 两棵树的关系

    维度current 树workInProgress 树
    可见性已提交，对应屏幕上的 DOM内存中的草稿，用户看不到中间状态
    数据来源上一次提交的 memoizedProps本轮新的 pendingProps
    可中断性已稳定，不可丢弃可被中断、丢弃，不影响屏幕
    指针FiberRoot.current 指向它通过 alternate 与 current 互相指向
    提交后变成下一轮 WIP 的候选成为新的 current 树
     
    FiberRoot.current ──→ current 树 A（已提交，屏幕所见）
                          │
                        alternate（互相指向）
                          ↓
                     workInProgress 树 B（构建中，不可见）

    ② 一次更新的完整时间线

    1. 更新前：root.current 指向树 A；树 A 的 alternate 为 null（首次更新时）或指向上一次被替换下来的树。
    2. render 阶段：renderRootSync 调用 createWorkInProgress(current) 得到 WIP 根；beginWork / reconcileChildren 在 WIP 上建立 child / sibling 链，并标记 effectTag。此时真实 DOM 完全没变。
    3. commit 阶段：commitRoot 先收集并处理 deletions，再按 PLACEMENT / UPDATE 操作 DOM，最后执行 root.current = finishedWork。
    4. 提交后：树 B 成为新的 current；树 A 通过 alternate 留下来，成为下一次更新的 WIP 候选。两棵树角色互换，对象不销毁。
    状态 1（首次提交后）
  FiberRoot.current → 树 A
  树 A.alternate = null

状态 2（第 N 次更新 · render）
  createWorkInProgress(A) → 新建 WIP 根 B
  A.alternate = B，B.alternate = A
  B 从 A 复制 stateNode / memoizedState，清空 child / sibling / effectTag
  reconcileChildren 在 B 上建树、打标

状态 3（commit）
  collectDeletions(B) → 删除旧节点
  commitWork(B.child) → PLACEMENT / UPDATE 映射到 DOM
  root.current = B

状态 4（提交后）
  FiberRoot.current → 树 B
  B.alternate = A（A 成为下一轮 WIP 候选）

    ③ 节点级复用：createWorkInProgress

    双缓存不是「整棵树全部重建」，而是逐节点复用 alternate 对象。同一个 Fiber 位置在两棵树中各有一个对象，更新时把旧对象改造成新一轮的 WIP：

    处理方式字段原因
    保留stateNode沿用真实 DOM 节点，避免重建导致焦点、滚动位置丢失
    保留memoizedStateHooks 状态链表和更新队列延续，组件状态不丢失
    复制memoizedProps作为上一次已提交属性的基准
    覆盖type / key / return / pendingProps反映本轮元素类型、父节点与待处理属性
    重置child / sibling / effectTag / deletions新一轮协调会重新生成子树结构与副作用标记
     
    export function createWorkInProgress(current, pendingProps = current.pendingProps, returnFiber = current.return) {
  let workInProgress = current.alternate;
  if (workInProgress === null) {
    workInProgress = createFiber(current.tag, current.type, current.key, pendingProps, returnFiber, current.stateNode);
    workInProgress.alternate = current;
    current.alternate = workInProgress;
  } else {
    workInProgress.type = current.type;
    workInProgress.key = current.key;
    workInProgress.return = returnFiber;
    workInProgress.stateNode = current.stateNode;
    workInProgress.pendingProps = pendingProps;
  }

  workInProgress.memoizedProps = current.memoizedProps;
  workInProgress.memoizedState = current.memoizedState;
  workInProgress.child = null;
  workInProgress.sibling = null;
  workInProgress.effectTag = null;
  workInProgress.deletions = [];
  return workInProgress;
}

    注意 alternate 互指只在第一次建立；后续更新直接复用那个旧 WIP 对象。因此连续更新时，两棵树的节点对象数量保持稳定，不会无限增长。

    ④ 为什么必须有双缓存

    • 可中断渲染：render 在 WIP 上进行，若被调度器打断或渲染出错，屏幕仍是完整的旧树，不会出现半成品 UI；恢复时继续处理 WIP 即可。
    • 提供 diff 基准：只有同时保留旧树，reconcileChildren 才能取 workInProgress.alternate.child 与新的 element 逐项比较 type/key，决定 UPDATE / PLACEMENT / DELETION。
    • 复用实例与状态：stateNode 让 DOM 不重建，memoizedState 让 Hooks 状态延续，避免组件每次更新都回到初始状态。
    • 提交集中且一致：所有 DOM 变更集中在 commit 阶段完成，最后一步才切换 root.current，用户看到的是一致的新状态。
    • 如果只改一棵树：会失去比较基准、无法保留旧状态，并且渲染过程中可能产生用户可见的中间态。

    ⑤ 与协调、Hooks、提交的衔接

    • render 入口：renderRootSync 中 const workInProgress = createWorkInProgress(current, current.pendingProps, null)，整轮工作都围绕这棵 WIP 展开。
    • 协调：reconcileChildren 从 workInProgress.alternate.child 取旧 Fiber 链；可复用则标记 UPDATE，否则新建并标记 PLACEMENT，旧 Fiber 进入 deletions。
    • Hooks：renderWithHooks 用 alternate === null 判断是首次挂载还是更新；updateWorkInProgressHook 沿 WIP 的 alternate.memoizedState 按调用顺序取回上次状态。
    • 提交：commitRoot 执行删除、插入、更新后，把 root.finishedWork 记为 WIP，并令 root.current = finishedWork，完成角色互换。
    function commitRoot(root, finishedWork) {
  const deletions = [];
  collectDeletions(finishedWork, deletions);
  for (const deletion of deletions) {
    commitDeletion(deletion, root.containerInfo);
  }
  commitWork(finishedWork.child, root.containerInfo);
  root.finishedWork = finishedWork;
  root.current = finishedWork;
}
    副作用标记的生命周期：effectTag 在 render 阶段写到 WIP 上，commit 阶段读取并执行；它不会在 commit 中清空，而是在该节点下一次被 createWorkInProgress 复用时重置为 null。这也是双缓存「两棵树交替复用」的直接体现。

    6. Fiber 循环遍历算法

    Fiber 的循环遍历本质是一次不用递归、可暂停的深度优先遍历。它只靠 child / sibling / return 三个指针推进，用一个 nextUnitOfWork 指针记住「下一个要处理的节点」。

    ① 三层循环

    层级代码位置作用
    调度循环flushScheduledRoots从待更新 root 集合中取出 root，逐个执行 render + commit
    render 遍历renderRootSync + performUnitOfWork构建 WIP 树，给节点打 effectTag
    commit 遍历commitRoot + commitWork把 effectTag 翻译成 DOM 操作
     
    function renderRootSync(root) {
  const current = root.current;
  const workInProgress = createWorkInProgress(current, current.pendingProps, null);
  let nextUnitOfWork = workInProgress;
  while (nextUnitOfWork !== null) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  return workInProgress;
}

    关键点是：nextUnitOfWork 是一个可保存的单一指针。每处理完一个 Fiber，函数就返回下一个 Fiber；调度器完全可以在两次调用之间暂停。

    ② 核心算法：performUnitOfWork

    function performUnitOfWork(fiber) {
  beginWork(fiber);
  if (fiber.child !== null) {
    return fiber.child;
  }
  let completedFiber = fiber;
  while (completedFiber !== null) {
    completeWork(completedFiber);
    if (completedFiber.sibling !== null) {
      return completedFiber.sibling;
    }
    completedFiber = completedFiber.return;
  }
  return null;
}

    拆开看只有两条路径：

    路径 A：有 child，就继续向下

    beginWork(fiber);
if (fiber.child !== null) {
  return fiber.child;
}

    beginWork 会执行组件、协调 children，并设置 fiber.child 和兄弟链。只要还有第一个孩子，就把孩子作为下一个工作单元。

    路径 B：没有 child，就完成并回溯

    let completedFiber = fiber;
while (completedFiber !== null) {
  completeWork(completedFiber);
  if (completedFiber.sibling !== null) {
    return completedFiber.sibling;
  }
  completedFiber = completedFiber.return;
}
    1. 调用 completeWork 完成该节点（新宿主节点在这里创建 DOM 实例）。
    2. 有 sibling → 转到兄弟节点，继续处理兄弟子树。
    3. 没有 sibling → 沿 return 回到父节点，重复上述过程。
    4. 一直回到根且根也没有兄弟 → completedFiber 变为 null，整棵树遍历结束。
    口诀：先 child，后 sibling，再 return；向下 beginWork，向上 completeWork。

    ③ 完整遍历示例

    HostRoot
  └─ div
       ├─ h1
       │   └─ text1
       └─ p
           └─ text2
    轮次当前 FiberbeginWork 后后续动作下一个工作单元
    1HostRoot生成 child = div有 child，直接向下div
    2div生成 child = h1，h1.sibling = p有 child，直接向下h1
    3h1生成 child = text1有 child，直接向下text1
    4text1文本节点无 childcompleteWork(text1)；无 sibling → 回到 h1；completeWork(h1)；h1.sibling = pp
    5p生成 child = text2有 child，直接向下text2
    6text2无 childcompleteWork(text2)；回 p → completeWork(p)；回 div → completeWork(div)；回 HostRoot → completeWork(HostRoot)；根无 returnnull，结束
    • 兄弟节点在整棵子树完成后才访问：p 是在 h1 整个子树（含 text1）完成后的第 4 轮末尾才被选中。
    • 每个 Fiber 的 completeWork 只调用一次：h1 的 complete 发生在从 text1 回溯时，而不是在 beginWork(h1) 之后立刻调用。

    ④ 为什么用 return 当隐式栈

    递归遍历写起来更简单，但有两个问题：

    function walk(fiber) {
  beginWork(fiber);
  if (fiber.child) walk(fiber.child);
  completeWork(fiber);
  if (fiber.sibling) walk(fiber.sibling);
}
    • 调用栈不能暂停：浏览器无法在中途保存 JS 调用栈，做不到时间切片。
    • 深树可能爆栈：递归层数受 JS 调用栈限制。

    Fiber 把「栈」信息存进节点本身：return 相当于递归返回地址，sibling 相当于当前层还没处理完的后续任务，nextUnitOfWork 相当于程序计数器。因此遍历状态只有一个指针，随时可以中断和恢复。教学版用同步 while 循环跑完，但结构已具备可中断条件。

    ⑤ beginWork 与 completeWork 的分工

    export function beginWork(workInProgress) {
  switch (workInProgress.tag) {
    case HostRoot:
      reconcileChildren(workInProgress, workInProgress.pendingProps.children);
      return;
    case FunctionComponent: {
      renderWithHooks(workInProgress);
      const children = workInProgress.type(workInProgress.pendingProps);
      resetHooks();
      reconcileChildren(workInProgress, children);
      return;
    }
    case HostComponent:
      reconcileChildren(workInProgress, workInProgress.pendingProps.children);
      return;
    default:
      return;
  }
}
    • beginWork：自顶向下，执行组件函数、协调子节点、生成 child/sibling 链、打 effectTag。
    • completeWork：自底向上，只为新建的 HostComponent / HostText 创建真实 DOM 实例；复用节点跳过。

    DOM 实例的创建发生在「回溯」阶段，而不是「下降」阶段。

    ⑥ 被遍历的链表由谁生成

    if (previousFiber === null) {
  workInProgress.child = newFiber;
} else {
  previousFiber.sibling = newFiber;
}
previousFiber = newFiber;
oldFiber = oldFiber.sibling;

    reconcileChildren 按索引逐个比较 oldFiber 与 element：

    • type/key 相同 → createWorkInProgress 复用，标记 UPDATE
    • 不同 → createFiberFromElement 新建，标记 PLACEMENT，旧节点进入 deletions
    • 新 children 更短 → 剩余旧 Fiber 全部标记 DELETION

    所以遍历算法本身不关心「children 数组」，它只认识 child 和 sibling。

    ⑦ commit 阶段的遍历不同

    render 遍历是「可中断、可丢弃」的；commit 遍历是同步执行、不可中断的，而且不再沿 return 回溯：

    function commitWork(fiber, rootContainer) {
  if (fiber.tag === HostComponent || fiber.tag === HostText) {
    const parentNode = getParentNode(fiber, rootContainer);
    setFiberForNode(fiber.stateNode, fiber);

    if (fiber.effectTag === PLACEMENT) {
      if (parentNode === rootContainer) {
        appendChildToContainer(rootContainer, fiber.stateNode);
      } else {
        parentNode.appendChild(fiber.stateNode);
      }
    } else if (fiber.effectTag === UPDATE) {
      if (fiber.tag === HostText) {
        commitTextUpdate(fiber.stateNode, fiber.alternate.pendingProps.content, fiber.pendingProps.content);
      } else {
        commitUpdate(fiber.stateNode, fiber.pendingProps);
      }
    }
  }

  let child = fiber.child;
  while (child !== null) {
    commitWork(child, rootContainer);
    child = child.sibling;
  }
}
    • render 遍历需要 return 来回溯并完成父节点；commit 遍历只沿 child → sibling 深度优先下降。
    • 需要父 DOM 时，用 getHostParentFiber(fiber) 沿 return 向上找最近的宿主父 Fiber（跳过函数组件）。
    • 删除操作不在 commitWork 里：collectDeletions 先递归收集 deletions，统一先删除再插入/更新。

    ⑧ 复杂度与关键性质

    • 每个 Fiber 在 render 阶段被访问恰好一次，时间复杂度 O(n)。
    • 空间上不需要额外的递归栈，靠 return 复用树结构，空间为 O(1) 额外指针。
    • beginWork 是前序遍历，completeWork 是后序遍历，一次循环同时完成两种顺序。
    • 中断后恢复只需保留 nextUnitOfWork，不需要重头开始。
    • commit 阶段不可中断，保证 DOM 变更一次性完成。
    一句话总结：Fiber 循环遍历就是把递归 DFS 拆成「一个 Fiber 一个工作单元」——有 child 就向下，没 child 就 complete 并借 sibling 横向移动，没有 sibling 就沿 return 上升，直到回到根；整个过程由一个可保存的 nextUnitOfWork 指针驱动。

    7. 使用方法（API）

    模块对外导出 5 个工厂函数，实际项目中通常不直接手写 Fiber，而是由 reconciler 自动调用；但调试与扩展时按下面方式使用：

    ① createFiber：底层构造

    createFiber(tag, type, key, pendingProps, returnFiber, stateNode = null)

    手动构造一个节点时，至少要传 tag/type/key/pendingProps/return。child、sibling、alternate 初始为 null，由后续阶段补齐。

    ② createFiberFromElement / createFiberFromText：由内容创建

    export function createFiberFromElement(element, returnFiber) {
  return createFiber(inferTag(element.type), element.type, element.key, element.props, returnFiber);
}

export function createFiberFromText(content, returnFiber) {
  return createFiber(HostText, REACT_TEXT_ELEMENT_TYPE, null, { content: String(content) }, returnFiber);
}

    reconcileChildren 中：可复用时走 createWorkInProgress(oldFiber, element.props, parent) 并标记 UPDATE；不可复用时走 createFiberFromElement 并标记 PLACEMENT，旧 Fiber 标记 DELETION 后推入 deletions。

    ③ createHostRootFiber + createFiberRoot：建立根

    const root = { containerInfo, current: null, finishedWork: null };
const hostRootFiber = createHostRootFiber();      // tag = HostRoot
hostRootFiber.stateNode = root;                   // Fiber → FiberRoot
root.current = hostRootFiber;                     // FiberRoot → 当前 Fiber 树

    ④ createWorkInProgress：每次更新复用

    const current = root.current;
const workInProgress = createWorkInProgress(current, current.pendingProps, null);
// workInProgress.alternate === current
// workInProgress.stateNode === current.stateNode（DOM 不重建）

    ⑤ 连接父子与兄弟

    workInProgress.child = firstChild;       // 第一个孩子
firstChild.return = workInProgress;      // 指回父亲
firstChild.sibling = secondChild;        // 下一个兄弟
secondChild.return = workInProgress;
    完整链路：createContainer → createFiberRoot 建立根；setState → scheduleUpdateOnFiber → renderRootSync 创建 WIP；beginWork/reconcileChildren 连接树并打标；completeWork 创建宿主实例；commitRoot 把标记映射到 DOM 并切换 root.current。

    8. 易错点

    • 函数组件没有 stateNode：commit 阶段用 getHostParentFiber 沿 return 跳过函数组件，找最近的宿主父节点。
    • child 不是 children 数组：所有子节点通过 sibling 横向串联，遍历时要 while (fiber.sibling !== null)。
    • 先删后改：commitRoot 先处理 deletions，再执行插入和更新，避免删掉刚插入的节点。
    • pendingProps 与 memoizedProps 不能混用：前者是本次要渲染的，后者是上次已提交的；状态更新比较应基于正确的那一侧。
    • Hooks 依赖顺序：memoizedState 是链表，useState 调用顺序变化会读到错误的 Hook；更新时 alternate 是否存在决定 mount 还是 update dispatcher。
    • effectTag 不会在 commit 中清空：下次 createWorkInProgress 复用时才重置为 null，不要假设提交后节点标记自动消失。
